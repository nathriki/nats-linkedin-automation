## Problem Statement

Build an automated pipeline that finds trending Philippine news/issues relevant to corporate and office workers (labor policy, wages, RTO mandates, contractualization, government actions affecting workers — broader than "corruption" alone) and turns them into storytelling/personal-angle LinkedIn posts, aimed first at Filipino corporate/BPO employees.

## What Makes This Cool

A voice that never misses a news cycle on issues Filipino office workers actually feel day-to-day, told as relatable stories instead of generic hot-takes — differentiated from existing PH commentary accounts by being automated and consistent rather than manual and sporadic.

## Constraints

- Storytelling/personal-angle format was chosen specifically for engagement, but a bot has no genuine personal experience to draw on.
- LinkedIn's 2026 algorithm actively suppresses generic/templated AI content and rewards first-person authenticity signals and specific data (source: web research, see Cross-Model Perspective note below — no cross-model run this session, this came from Phase 2.75 landscape search).
- Philippine cyber libel carries a penalty one degree higher than ordinary libel specifically because it's committed via a "computer system" (social media qualifies). "Opinion framing" is not a reliable defense against statements that imply false facts about identifiable people or companies.
- LinkedIn's `w_member_social` posting scope (posting to your OWN profile, per Premise 6) is an Open Permission — self-serve and instant, no app review required. This is NOT the same as `w_organization_social` (posting to a company/org PAGE), which does require weeks-to-months Marketing Developer Platform partner review. Corrected during /plan-eng-review after a prior draft of this doc conflated the two (likely carried over from a different, org-page project) — verify against the LinkedIn developer console before building, but treat this as a low-risk item, not a go/no-go blocker.
- Scraping PH news sites for source content carries its own copyright/ToS exposure, separate from the cyber-libel risk on the posting side. This got one sentence and no follow-through in the original review pass — see the corresponding Open Question and Next Step, added after outside-voice review caught the asymmetry with how thoroughly the libel risk was treated. (plan-eng-review, outside voice finding 8)
- Greenfield repo — no existing code to reuse. NATS is the intended backbone (per repo name and user intent); running a NATS+JetStream broker for a single-user, daily-cadence workload is real ops overhead, accepted here because the pipeline stages (source, score, draft, classify, post) are expected to grow independently (more sources, other platforms) rather than staying single-purpose.
- "Distribution" = posting to the user's own LinkedIn account, not shipping a product to other users.
- Secrets (LinkedIn OAuth token, Telegram bot token, LLM API key) live in environment variables loaded from a gitignored `.env` file, never in NATS message payloads, logs, or committed config. (plan-eng-review, architecture issue 1)
- NATS JetStream is at-least-once delivery: if the poster posts to LinkedIn successfully but crashes/disconnects before acking, the message redelivers and the SAME story posts twice. See the dedup-key requirement in Next Steps. (plan-eng-review, architecture issue 3)

## Premises

1. Content scope is trending PH news/issues relevant to corporate/office workers — broader than corruption alone, narrower than general news.
2. Format is storytelling/personal-angle posts, anchored in a disclosed composite worker archetype — never a fabricated "I personally experienced this" claim presented as genuine, and never a real person's story (restricted to composite archetypes only during /plan-eng-review, code quality issue 2 — this removes the Data Privacy Act 2012 compliance question entirely rather than deferring it).
3. Primary audience is Filipino corporate/BPO employees.
4. The pipeline is automated end-to-end except a review gate for any post naming a specific official/company or asserting a factual corruption claim.
5. NATS is the backbone connecting pipeline stages (scraper → scorer → drafter → risk-classifier → poster). The risk-classifier publishes directly to `post.approved` or `post.pending_review` based on its own verdict — no separate router service (folded during /plan-eng-review, architecture issue 2).
6. No distribution/packaging concerns beyond posting to the user's own LinkedIn account.

Rejected during session: fully-automated-with-zero-review (originally proposed) — rejected after landscape research showed PH cyber libel risk and LinkedIn's authenticity-scoring both cut against posting unreviewed, fabricated-personal-angle content about corruption/government actions.

## Approaches Considered

### Approach A: Minimal script pipeline (no NATS)
Single scheduled script: fetch news → LLM draft → regex-based risk check → Telegram approval for risky posts → auto-post the rest. Fastest to ship (S effort), but skips NATS entirely, contradicting the stated intent, and would need a rewrite to decouple stages later.

### Approach B: NATS-native pipeline (recommended, chosen)
Small worker processes communicating over NATS subjects: scraper → scorer (cheap heuristic, no LLM, ranks all candidates) → drafter + risk-classifier (LLM, run only on the top 1-3 scored candidates; classifier publishes directly to `post.approved` or `post.pending_review`) → Telegram/Slack approval bot → poster. JetStream persists every draft and decision, giving an audit trail that matters given the libel exposure. M-L effort, each stage independently testable/swappable.

### Approach C: Editorial-desk model (every post human-curated)
Same NATS backbone as B, but every draft — not just flagged ones — goes into a daily digest for the user to pick/edit/approve. Lowest legal risk and best authenticity (a human touches every story), but not "fully automated" and throughput is capped by review time.

## Recommended Approach

**Approach B: NATS-native pipeline**, chosen by the user. Matches the project's stated intent (NATS backbone), keeps the pipeline mostly automated while gating only the legally risky subset (named officials/companies, factual corruption claims) through human review, and gives each stage (source, score, draft, classify, post) room to grow independently — e.g. adding new news sources or cross-posting to another platform later without a rewrite. Reaffirmed during /plan-eng-review after both the internal Step 0 scope challenge and an independent outside-voice review raised the same "this could be simpler" concern — the user weighed it twice with full context and kept the per-stage independence over solo-deployment simplicity both times. (outside voice tension 3)

## Open Questions

- **Must resolve before the subject schema is frozen** (Next Step 2 depends on this, not the other way around — sequencing corrected after outside-voice review): which news sources feed the scraper (PH news RSS feeds, X/Twitter trends, Reddit r/Philippines, Google Trends PH, PSA/DOLE releases). RSS, a Twitter/X API, Reddit, and Google Trends all produce structurally different payloads, so the source(s) must be picked before `news.raw`'s shape can be fixed. (plan-eng-review, outside voice finding 4)
- **Must resolve before scraping any source**: for each candidate source, check its ToS/robots.txt for redistribution terms; prefer sources with an official RSS feed sanctioned for this kind of reuse, and avoid full-text reproduction (link back + short excerpt) rather than assuming scraping is fine because the libel risk got more attention. (plan-eng-review, outside voice finding 8)
- **Must resolve before the drafter is built**: no Next Step or Task currently exists for the "which LLM + what concrete mechanism enforces composite-archetype framing" question below, even though it's flagged as load-bearing — see Next Steps for the now-added step. (plan-eng-review, outside voice finding 5)
- What does the scorer actually score for — relevance to the target audience, general engagement potential, or both? Now specified as a cheap heuristic/keyword pass (no LLM call) that ranks all candidates so only the top 1-3 go through the expensive drafter+classifier LLM calls (plan-eng-review, performance issue 1) — exact scoring signal still undefined.
- **Must resolve before the drafter is built** (load-bearing for the doc's central legal/authenticity argument): which LLM powers the drafter, and what concrete mechanism enforces the "disclosed composite archetype" framing in the prompt — this is the thing standing between the pipeline and fabricated first-person claims, so it can't stay a loose prompt instruction.
- **Must resolve before the poster service goes live** (load-bearing for the doc's libel-safety argument): exact risk-classifier rule set (keyword list, named-entity detection, or LLM-based classification), and — critically — what happens on a false negative, i.e. a risky post the classifier misses and auto-posts. The classifier is the single gate protecting against the cyber-libel exposure described in Constraints; its reliability is not yet a solved problem.
- **Must resolve before the poster service goes live**: define a dedup key (e.g. source URL hash + publish date) in the message payload, and require the poster to check it against a small local store of already-posted IDs before posting — closes the JetStream at-least-once double-post risk in Constraints. (plan-eng-review, architecture issue 3)
- **Must resolve before the poster service goes live**: incident-response process if a published post turns out risky (classifier false negative, or a fact later disproven) — manual deletion vs. a documented retraction post, and whether to notify anyone. Elevated from a non-blocking Reviewer Concern to match the classifier-reliability gate. (plan-eng-review, code quality issue 1)
- **Must resolve before the poster service goes live**: kill-switch definition — what counts as "repeated misses" (e.g. 2 risky posts auto-published within 24h) and the automatic response (pause the poster's subscription, alert the user). Elevated from a non-blocking Reviewer Concern to match the classifier-reliability gate. (plan-eng-review, code quality issue 1)
- **Must resolve before the poster service goes live**: build a held-out eval set of 15-20 labeled examples (mix of safe/risky news items) and require the risk-classifier to hit a defined false-negative rate on them, plus a smaller eval for the drafter's archetype-disclosure adherence — gives the classifier-reliability gate an actual measurable bar. (plan-eng-review, test gap 1)
- Where does the Telegram/Slack approval bot run, and who (just the user) has approval rights.
- Approval timeout: intentionally none — a pending-review post sits in `post.pending_review` indefinitely until reviewed (safe by default, since nothing risky auto-publishes). Optionally add a daily digest reminder if the pending queue isn't empty. (plan-eng-review, test gap 2 — documented as intended behavior, not a gap)
- Operational edge cases not yet designed for: zero-news days (does the pipeline skip a cycle, or is there a fallback content type?), and LinkedIn's own post-frequency/rate limits.
- **Must investigate before building the drafter/classifier** (outside voice tension 1): manually pull a week of real trending PH labor/corporate news and tag how many stories would trigger the Premise 4 review gate (name an official/company or assert a factual claim). If most on-topic trending stories trigger it, "automated end-to-end" collapses in practice to "AI drafts, human reviews almost everything daily" — which may still be valuable, but the plan should say so honestly rather than assume otherwise.
- **Must investigate before building the full pipeline** (outside voice tension 2): draft 3-5 sample posts in the disclosed-composite-archetype style and gut-check (or post 1-2 as a trial) whether disclosure undercuts engagement, given LinkedIn's algorithm rewards first-person authenticity signals and a disclosed composite is explicitly not that. This is the load-bearing assumption behind "What Makes This Cool" and was never tested against the engagement thesis, only the legal one.
- LinkedIn account-standing risk is a separate question from API scope approval: `w_member_social` access being self-serve (Constraints) doesn't clear whether LinkedIn's platform policy against automated/inauthentic posting behavior puts the account itself at risk of restriction. Research this specifically before the poster ships. (plan-eng-review, outside voice tension 4)
- No infrastructure monitoring exists for the pipeline itself (NATS/JetStream broker down, disk full, approval bot host offline) — only content failures (bad post) have a kill-switch. Add a minimal daily heartbeat check that alerts if no post/heartbeat happened in 24-36h, so a silent total outage doesn't undermine the "never misses a news cycle" promise. (plan-eng-review, outside voice tension 5)
- Message schema is subject names only so far (`news.raw`, `news.scored`, etc.) — payload fields (dedup key, timestamp, source) aren't defined yet; needed before Next Step 2.

## Success Criteria

- End-to-end pipeline runs on a schedule, producing at least one storytelling-format post per day without manual drafting effort (cadence adjustable once real throughput is known — daily is the starting target, not a hard constraint).
- Every post naming a specific official/company or asserting a factual corruption claim is held for human review before publishing — zero unreviewed risky posts.
- No fabricated "I personally experienced this" claims presented as genuine — every story is a disclosed composite archetype (never a real person's account, per Premise 2). Verified via periodic human spot-check of published posts against the drafter's source material (not just a one-time prompt review), since a drafting model can drift over time.
- NATS subjects/services are independently testable (each stage can be run and verified in isolation).

## Distribution Plan

Not applicable in the packaging sense — the only "distribution" is posting to the user's own LinkedIn account via the LinkedIn API (`w_member_social`, self-serve, no approval wait). No CI/CD/release pipeline needed for external users.

## Reviewer Concerns

Resolved during /plan-eng-review: the Data Privacy Act 2012 compliance question was removed by restricting Premise 2 to composite archetypes only (no real-person stories); the incident-response and kill-switch gaps were elevated to blocking Open Questions/Next Steps to match the risk-classifier reliability gate.

## NOT in scope

- Cross-posting to platforms other than LinkedIn (Twitter/X, Facebook) — Premise 6 scopes this to LinkedIn only; the NATS architecture leaves room to add later.
- Scraping more than one news source before the first is proven (Next Step 3) — deferred to keep the initial build small.
- Auto-expiry/escalation for pending-approval posts — explicitly rejected (test gap 2); posts stay pending indefinitely by design, not by omission.
- A dedicated secrets manager (Vault/1Password CLI) — gitignored `.env` env vars are enough for a solo pipeline (architecture issue 1); revisit only if this grows beyond one operator.
- A separate router service between the risk-classifier and the approval/poster subjects — folded into the classifier itself (architecture issue 2); nothing in this design calls for routing logic to evolve independently.
- Sourcing "real anonymized" worker stories from actual people — dropped entirely, not deferred (code quality issue 2); composite archetypes cover the authenticity goal without a Data Privacy Act 2012 compliance question.

## Worktree Parallelization Strategy

**Sequential prerequisites (corrected order after outside-voice review):** (1) pick the news source(s) first — RSS, Twitter/X, Reddit, and Google Trends each produce a structurally different payload, so the schema can't be responsibly frozen before this; (2) then fix the NATS subject schema (subject names + payload fields for `news.raw`, `news.scored`, `post.drafted`, `post.pending_review`, `post.approved`). Every other lane below builds against that frozen contract, not against another lane's implementation.

| Step | Modules touched | Depends on |
|------|----------------|------------|
| News source selection | (design only, no code) | — |
| Subject schema | (design only, no code) | News source selection |
| Scraper | `scraper/` | Subject schema |
| Scorer | `scorer/` | Subject schema |
| Drafter + risk-classifier + eval set | `drafter/`, `classifier/`, `eval/` | Subject schema |
| Approval bot | `approval-bot/` | Subject schema |
| Poster (+ dedup store) | `poster/` | Subject schema |

Lane A (sequential, blocks all others): finalize subject schema.
Lane B (parallel, independent): scraper.
Lane C (parallel, independent): scorer.
Lane D (parallel, independent): drafter + risk-classifier + eval-set creation (the eval examples themselves need no code and can start immediately, even during Lane A).
Lane E (parallel, independent): approval bot.
Lane F (parallel, independent): poster + dedup store.

Execution order: finish Lane A first (or at least freeze the schema), then launch B through F in parallel worktrees — each is independently testable against the frozen schema with mocked NATS pub/sub, matching the design's own stated goal of per-stage independence. Integrate all five against a real local NATS server once each lane's unit tests pass. No two lanes touch the same module directory, so there's no merge-conflict risk between them.
